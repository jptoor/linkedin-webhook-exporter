# Adversarial risk review: v0.3 capabilities

Reviewed 2026-09-04–05. Scope: the production manifest, MAIN-world response/clipboard bridge, normalization and enrichment, session authentication, external messaging, telemetry, and delivery. Existing UI, validation, queue, and logging code was traced where the new capabilities depend on it. Frontier's permission breadth is not evidence that these particular trust boundaries are safe. No P0 was established.

P1 means a release blocker involving unauthorized actions, disclosure across a trust boundary, or a missing account-safety control. P2 means a concrete privacy, resilience, or compatibility defect, including paths with additional prerequisites. Rankings reflect the implementation reviewed, not an assertion that an actual subdomain takeover or backend vulnerability exists.

The permission interpretation above follows Chrome's [cookies API documentation](https://developer.chrome.com/docs/extensions/reference/api/cookies): cookie access uses the combined cookie and host permissions, and Cookie objects include their values. Chrome also documents that extension requests with host permission can receive [same-site cookie treatment](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies); that enables session authentication, but does not authorize page-triggered actions. The error-report redirect distinction follows the [Fetch redirect algorithm](https://fetch.spec.whatwg.org/#http-redirect-fetch). The buffering issue is consistent with [Response.clone documentation](https://developer.mozilla.org/en-US/docs/Web/API/Response/clone).

## Validation and limits of the authors' evidence

Ran the existing `linkedin-api`, `telemetry-auth`, `worker`, `sender`, and `deepline` unit suites: **5 files, 67 tests passed**. Passing these tests does not contradict the findings. Separate temporary harnesses bundled the actual source with esbuild and used synthetic values, jsdom, or the repository's in-memory Chrome implementation. They reproduced:

- An untrusted DOM click (`isTrusted === false`) producing one `CAPTURE` message. This exercised the actual content script and dock handlers, without a browser extension network send.
- A forged, non-allow-listed response supplying `https://www.linkedin.com/in/wrong-person` for an existing Sales Nav identity; API summary also filled an otherwise-null About field.
- A payload exceeding 2 MB accepted by the normalizer.
- Reused XHR emitting `UNRELATED_RESPONSE` labeled as the previous `/voyager/api/graphql` response.
- An HTTPS `abandoned.deepline.com` sender receiving synthetic email/name/org details, while HTTP was rejected.
- Remote `intercept: false` leaving the content setting true.
- A queued request first attempted under mocked account A, then automatically retried under mocked account B with identical body and `credentials: include`; the queue contained no user/org binding.
- Error bodies/properties retaining synthetic bearer credentials, email, and session-bearing URLs; a signed-in default session plus a custom API-key destination routing its report to the custom host in cookie mode.
- A generic lead webhook body retaining a synthetic `sessionId` in `source.page_url`.

No real credentials, LinkedIn requests, Deepline runs, or third-party webhook sends were used. The browser acceptance suite was read, not rerun. AT-30 covers expected enrichment; AT-31 establishes that its fixture cookie is not in extension storage, not that Cookie objects omit values or that account changes are safe. Exact LinkedIn restriction probability, real Deepline cookie attributes, backend CSRF enforcement, cross-org play authorization, and actual subdomain ownership were not established by these local checks.

The authors' review needs corrections beyond the ranked defects: raw GraphQL/XHR bodies are broadcast before normalization, so “re-validates every URL before it can reach a payload” does not describe bridge traffic; the remote flags are not effective kill switches; and `get_auth_state` is more revealing than claimed. Declaring a MAIN-world content script avoids a web-accessible script resource, but is not a blanket CSP exemption: Chrome says the [page's CSP applies in MAIN world](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#content-security-policy).

## What is acceptable and why

- **Passive response observation, after the implementation defects are fixed.** The interception code delegates the original fetch/XHR request and does not introduce LinkedIn API pagination, retries, custom headers, or additional API requests. The original fetch promise is returned, and a clone is used for observation. Account restriction risk still includes detectable monkey-patching and data collection; there is no evidence here to quantify it or declare it safe because another vendor ships similar behavior. The clipboard hook's delayed writes, leaked reused-XHR responses, and ineffective shutdown are avoidable additions to that residual risk. The explicit share-search action may cause LinkedIn's ordinary UI to make requests; it is not passive observation.
- **MAIN-world data being readable and forgeable by MAIN-world scripts.** That is inherent to the chosen design. A malicious script already executing on LinkedIn can generally instrument its own page traffic. Posting it on a fixed channel is not a confidentiality or authenticity boundary, and raw responses must never contain extension credentials. This residual is acceptable only when such input cannot authorize sends and its enrichment is treated as untrusted. Ordinary profile text alone is not sufficient to run the JavaScript attacks above; they require page script execution, a compromised page dependency, or equivalent control.
- **Browser-managed Deepline session use for explicitly authorized operations.** The auth helper checks a fixed pair of cookie names and returns selected session fields, not the cookie. `fetchSession`, `apiInit`, and the sender reject redirects. API-key play requests use `credentials: omit`; ordinary webhooks also omit ambient cookies. No normal direct route was found from a Deepline cookie/API key into the page bridge or a webhook body. This remains acceptable only with CR-01/CR-04 fixed and an explicit origin/auth binding; an empty key must not silently confer unrelated cookie authority. Error reflection and telemetry remain separate exceptions requiring repair.
- **The external operation allow-list and HTTP rejection.** Unknown external operations cannot reach settings mutation, capture, basket send, or key retrieval. Other extensions are not granted external access because the manifest does not specify `ids`; see Chrome's [externally_connectable reference](https://developer.chrome.com/docs/extensions/reference/manifest/externally-connectable). Narrow first-party HTTPS origins returning minimal state can reasonably open a panel or report installation status. Trusting every Deepline subdomain with personal account details is not necessary to achieve that behavior.
- **Configured destinations and normalized people fields.** A user-selected HTTPS webhook/play host is an intended recipient, not automatically an exfiltration endpoint. Canonicalization rejects arbitrary hosts for public/company/Sales Nav URLs; image fields are restricted to HTTPS `licdn.com`; strings and outgoing lead counts are bounded. No generic bridge-to-arbitrary-fetch operation, page-selectable destination, or executed API JSON was found. A syntactically valid LinkedIn URL can still identify the wrong person, and downstream plays must not treat arbitrary lead strings as instructions. CR-01 can send to the active destination, but does not itself let the hostile page replace that destination or read its key.
- **Limited product analytics and optional network access.** Current product-event call sites send fixed event names and counts/categories rather than whole leads. No Segment request is attempted unless a write key is compiled in; Segment uses `credentials: omit`. The default manifest does not grant `api.segment.io` host access, so successful collection must not be assumed if that server does not allow the request through CORS. Optional HTTPS permissions are declared rather than all granted at install, and production scripts omit the test build's loopback matches. These are useful constraints, while CR-06/CR-07 and the cookie-permission expansion still require attention. User/org IDs make analytics pseudonymous, not anonymous.

## Verdict: DO NOT SHIP

The current implementation lets page code drive credentialed actions, lets every trusted-by-suffix subdomain read account PII, can retry a queued run under another identity, and cannot perform its advertised interception shutdown. These are implementation flaws beyond the inherent risk of passive LinkedIn observation. Close CR-01 through CR-05 before release; repair the P2 privacy and interception defects as part of that work and add regression coverage for the demonstrated paths. A follow-up review should verify trusted action gating in real Chromium, actual shutdown behavior in already-open tabs, and session/org binding against the intended backend.
